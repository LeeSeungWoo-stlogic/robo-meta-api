# T2SQL 동작 과정 기술 평가

- 평가 대상: `docs/T2SQL_자연어부터_동작로직.md`
- 평가일: 2026-08-19
- 평가 범위: 문서에 기술된 `/t2sql` 전체 처리 과정의 기술적 타당성, 안전성, 정확성, 운영성
- 실행 검증: `http://127.0.0.1:8101`에서 Q1·Q2의 `/t2sql`, `/query_execute`, 컨테이너 로그와 비교 SQL 확인
- 평가 한계: 실제 API 동작은 확인했으나 내부 소스 코드 정합성, 반복 부하, 전체 질문군 정확도는 별도 검증이 필요하다.

## 1. 종합 결론

현재 T2SQL은 **메타데이터 선계획 후 LLM이 제한된 범위에서 SQL을 생성하는 구조**다. 자연어를 SQL로 바로 변환하는 단순 LLM 방식보다 안전성과 추적성이 높다.

특히 다음 구조는 적절하다.

- Serving 승인 메타데이터만 사용
- 값 코드, FK, 팩트, 컬럼을 먼저 확정
- 계획 밖 테이블 사용 차단
- 이종 소스 JOIN 차단
- SELECT 전용 검증
- 실제 SQL 반환 전 MindsDB 실행 검증
- `generation_id`, `used_metadata`, `probe_summary` 제공
- 전체 벽시계와 단계별 timeout 적용

그러나 **SQL 실행 가능성 검증이 의미 정확성 검증을 대신하고 있다.** 실제 Q1은 정수장 목록 79개를 얻기 위해 불필요한 태그·별량 JOIN으로 중간 1,744,952행을 만들었지만 `generated`로 확정됐다. 실제 Q2는 기간 없는 질문을 2020-01-01부터 2026-12-31까지의 17개 태그, 39,423개 일 집계행 평균으로 해석했지만 이 유효 범위를 응답에서 설명하지 않았다.

두 요청 모두 코드가 있다는 이유로 confirm을 생략했다. JOIN 신뢰도는 최저 0.28인데 계획은 `complete`였다. `/query_execute`가 반환한 한글 명칭은 UTF-8 바이트가 문자 코드로 노출되는 형태로 깨졌다.

종합 평가는 **구조 양호, 실행 품질 개선 필요**다. 운영 적용 가능한 기반은 갖췄지만, JOIN 필요성·집계 의미·기간 의미·응답 인코딩 P0 항목 보완 전에는 고신뢰 자동 질의 시스템으로 보기 어렵다.

## 1.1 실API 검증 결과

### 검증 방법

1. 문서 Q1·Q2를 기본 요청값으로 `POST /t2sql`에 전송
2. 반환 SQL을 `POST /query_execute`로 실행
3. 단순 기준 SQL과 진단 집계 SQL로 결과 범위·중간행·집계 산식 비교
4. `robo-meta-api-meaning` 컨테이너의 같은 시간대 로그 확인

서버 상태:

- 컨테이너: `robo-meta-api-meaning`
- 포트: 호스트 `8101` → 컨테이너 `8100`
- 상태: healthy

### Q1 — `금강권역 정수장 목록`

실행 결과:

- HTTP: 200
- `generation_id`: `8dd0dd25-6f7e-466c-8622-7ce5e02ce86c`
- `sql_status`: `generated`
- 서버 `elapsed_ms`: 17,484.2ms
- 클라이언트 관측: 17.509초
- 의미 분석: `procedure=list`, `target=금강권역`, `answer_axis=["정수장"]`
- 범위 코드: `금강유역본부(충청)` → `902`
- confirm: 생략
- probe: 0회
- 실제 조회 결과: 79행

생성 SQL의 테이블:

- `rdibonbu_tb`: 지역본부
- `rdisaup_tb`: 사업장
- `rditag_tb`: 태그 bridge
- `rdibyun_tb`: 별량코드

기술 판정:

- 질문 답에는 지역본부와 사업장만 필요하다.
- `rdibyun_tb`가 required table로 들어가면서 `rditag_tb`가 bridge로 추가됐다.
- 지역본부→별량코드 경로 신뢰도는 0.28인데 계획은 `complete`였다.
- 생성 JOIN은 사업장과 태그를 사업장 키가 아닌 `BNB_CODE`만으로 연결했다.
- 진단 SQL에서 중간 JOIN 결과는 1,744,952행이었다.
- `DISTINCT`가 이를 79개 정수장으로 축소했다.
- 태그·별량 JOIN 없는 `rdisaup_tb WHERE BNB_CODE='902'` 기준 결과도 79개였다.

결론:

> 결과 집합은 기준 목록과 같았지만 계획이 불필요한 역할을 채택해 대규모 fan-out을 만들었다. 실행 성공과 79행 반환만으로는 이 문제를 검출할 수 없다.

### Q2 — `화성정수장 평균 탁도`

실행 결과:

- HTTP: 200
- `generation_id`: `fd59b5e8-e4a7-4bc1-ac17-4c5be7ff9cc0`
- `sql_status`: `generated`
- 서버 `elapsed_ms`: 12,009.8ms
- 클라이언트 관측: 12.040초
- 의미 분석: `procedure=aggregate`, `metric=탁도`, `target=화성정수장`
- 사업장 코드: `화성정수장` → `617`
- 측정 코드: `탁 도` → `TB`
- 팩트: `rdd01dd_tb` 일 DATA
- confirm: 생략
- probe: 0회
- 실제 결과: 1행, 평균 `0.05877279760545874`

실제 집계 범위:

- 최소 일자: `20200101`
- 최대 일자: `20261231`
- 탁도 태그: 17개
- 일 집계행: 39,423개
- `CNT` 합계: 943,709
- 행별 `CNT` 범위: 8–24

집계 산식 비교:

- 생성 SQL: `AVG(VAL)` = `0.05877279760545874`
- `CNT` 가중 평균: `SUM(VAL * CNT) / SUM(CNT)` = `0.05889527386090416`
- 차이: 약 0.21%

기술 판정:

- `required_columns`에는 `VAL`과 `CNT`가 모두 들어갔지만 SQL은 `CNT`를 사용하지 않았다.
- 메타데이터 설명은 `VAL`을 일일 수치, `CNT`를 기록 건수로만 설명한다. `AVG(VAL)`과 `CNT` 가중 평균 중 어느 것이 업무 정답인지 계획에 없다.
- 질문에 기간이 없으므로 엔진 정책대로 기간 필터를 만들지 않았다.
- 결과적으로 2020년부터 2026년 말까지 전기간을 자동 집계했다.
- 현재 평가일 이후인 2026년 12월 데이터까지 포함된다. 데이터 적재 특성일 수 있으나 사용자에게 유효 범위가 드러나지 않는다.
- 팩트→태그 JOIN 신뢰도는 0.35, 태그→사업장·별량 JOIN 신뢰도는 0.28인데 계획은 `complete`였다.

결론:

> SQL은 실행되고 숫자도 반환했다. 그러나 평균의 모집단, 가중치, 기간이 구조화된 계획으로 확정되지 않았다. 실행 검증은 집계 의미를 검증하지 못했다.

### `/query_execute` 응답 인코딩

관찰:

- Q1의 `BNB_NAME`, `SUJ_NAME`과 Q2의 `SUJ_NAME`이 깨진 문자열로 반환됐다.
- 단순 `SELECT SUJ_NAME ... LIMIT 1`에서도 동일했다.
- 반환 문자열 코드포인트 앞부분은 `235,176,152,234,179,161,...`이었다.
- 이는 한글 UTF-8 바이트열이 Unicode 문자값처럼 노출된 패턴이다.
- `/t2sql` 메타데이터 내부의 한글 `natural_value`, 설명, 예시는 정상이다.

판정:

> 원천 데이터 자체보다 `/query_execute` 또는 MindsDB 결과 변환 경로의 인코딩 문제로 좁혀진다. 사용자 결과 명칭을 훼손하므로 P0 결함이다.

### 로그 관측 결과

로그에서 확인된 단계:

- `decide start`
- 의미 분석 시작·완료
- needle 구성
- glossary 건수
- range·metric mapping 건수
- catalog/store 결과
- confirm 생략과 필터값
- HTTP access log

확인되지 않은 정보:

- 팩트 후보와 선정 이유
- required table 채택 이유
- JOIN 경로별 선택·탈락 이유
- 낮은 신뢰도 경로를 `complete`로 승인한 근거
- SQL 생성 시도
- 가드 통과 내역
- validation SQL과 결과
- 단계별 generate·validate 소요 시간
- `/query_execute` 내부 datasource 실행·인코딩 단계

시간 구간:

- Q1: 시작→confirm 생략 5.893초, confirm 생략→HTTP 200 11.592초
- Q2: 시작→confirm 생략 4.813초, confirm 생략→HTTP 200 7.196초
- 후반 11.592초·7.196초 구간에 생성과 validation이 포함되지만 내부 단계 로그가 없다.

판정:

> 응답은 상세하지만 서버 로그만으로 생성·검증 문제를 재구성하기 어렵다. 운영 장애와 오답 분석에 필요한 stage telemetry가 부족하다.

## 2. 항목별 평가

### 2.1 안전성: 우수

강점:

- SELECT 또는 `WITH ... SELECT` 한 문장만 허용한다.
- Serving allowlist 밖 객체를 거부한다.
- 계획에 없는 테이블을 거부한다.
- 승인 FK의 ON 컬럼을 검사한다.
- master/code 이외 표에 필터 없는 조회를 제한한다.
- 이종 DB JOIN을 명시적으로 차단한다.
- 검증용 SQL에만 행 제한을 추가하고 공개 SQL은 보존한다.
- MindsDB 실행 입구에서도 비조회 문장을 재차 차단한다.

잔여 위험:

- 문서는 SQL 검증이 AST 기반인지 문자열 기반인지 밝히지 않는다.
- JOIN 가드는 승인 ON 컬럼명이 SQL에 존재하는지만 검사하는 것으로 읽힌다. 컬럼 존재만으로 실제 ON 식의 방향, 별칭, 연산자, 테이블 쌍이 정확하다고 보장할 수 없다.
- 실패 응답에 마지막 SQL 초안이 포함될 수 있다. 클라이언트가 `sql_status`를 무시하면 검증 실패 SQL을 실행할 위험이 있다.
- `LIKE '%mention%'` probe는 wildcard escape, 최대 문자열 길이, 실행 계획 통제가 문서에 없다.

판정:

> 읽기 전용 방어는 강하다. 의미상 잘못된 조회와 비효율 조회 방어는 추가 필요하다.

### 2.2 계획 정확성: 보통

강점:

- 의미 분해와 스토어 검색을 분리했다.
- 값매핑, 카탈로그, FK, 팩트, 필터, 필수 컬럼 순서가 명확하다.
- 팩트가 필요한 질문과 필요 없는 질문을 구분한다.
- 범위 코드가 미결합이면 SQL을 만들지 않는 fail-closed 정책을 사용한다.
- 값 코드와 승인 FK를 계획에 고정해 LLM 자유도를 낮춘다.

문제:

1. **정확한 코드가 아니라 유일한 코드라는 이유로 확정될 수 있다.**
   - 범위 매핑은 distinct 코드가 1개면 확정한다.
   - 후보 생성이나 별칭 규칙이 잘못되면 단일 오답도 확정된다.
   - 유일성은 정확성 증거가 아니다.

2. **짧은 라벨 제거 규칙이 서로 다른 코드를 소거할 수 있다.**
   - 원문도 괄호 머리가 같은 두 코드에서 한 행이 삭제될 수 있음을 명시한다.
   - 이는 알려진 정확성 결함이다.
   - 문자열 길이보다 코드, 표, 컬럼, 엔티티 유형, 문맥 점수를 함께 비교해야 한다.

3. **팩트 선정이 휴리스틱 축소에 과도하게 의존한다.**
   - 후보 두 개가 남으면 `팩트 표 미선정`으로 종료한다.
   - 잘못된 자동 선택은 막지만, 정상 질문의 성공률이 낮아질 수 있다.
   - 후보별 근거 점수와 사용자 확인 경로가 없다.

4. **confirm 생략 조건이 강하다.**
   - resolved 코드가 있으면 confirm을 생략할 수 있다.
   - 앞 단계에서 틀린 코드를 확정하면 의미 검증 없이 SQL 생성으로 진행한다.
   - confirm은 “코드 존재”보다 “질문 언급과 코드 의미의 일치”를 검증해야 한다.

5. **의미 분석 실패 시 품질 저하 폭이 크다.**
   - 질문 토큰 기반 검색으로 전환하지만 값매핑과 필터 생성 능력이 크게 줄어든다.
   - `hyde_enabled`, embedding API key가 의미 LLM 실행 조건에 연결된 이유도 계약상 불명확하다.

판정:

> 계획 우선 구조는 맞다. 단일 후보 확정, 라벨 소거, confirm 생략 규칙이 오선정 전파를 만들 수 있다.

### 2.3 검색·엔티티 해석 견고성: 미흡

현재 표 검색은 임베딩 검색이 아니며 동등·머리·접두 중심이다. 장점은 결정성과 설명 가능성이다. 단점은 사용자 표현 변화에 취약하다는 점이다.

취약 사례:

- 띄어쓰기와 조사가 예상 패턴과 다른 질문
- 오탈자
- 약칭과 현업 별칭
- 어순 변화
- “탁도 평균” 대신 “물이 얼마나 흐린지 평균” 같은 우회 표현
- 복합 범위 또는 제외 조건
- 동일 표면이 여러 업무 엔티티에서 쓰이는 경우

본부·사업장 접미 사전은 현재 도메인에서 효과적이다. 다만 규칙 추가가 누적되면 도메인별 예외 엔진이 될 위험이 있다.

개선 방향:

- 동등 적중을 최우선으로 유지
- 승인 용어·동의어 기반 정규화 추가
- 의미 검색은 후보 생성에만 사용
- 최종 확정은 승인 메타데이터와 코드 관계로 제한
- 모든 후보에 `match_type`, `score`, `evidence` 기록
- 낮은 신뢰도 또는 근소한 점수 차이는 자동 확정 금지

### 2.4 SQL 생성·검증: 보통

강점:

- 생성 입력을 질문, 분석, 계획, 용어집, 엔티티, probe 결과로 제한한다.
- `required_tables`, `required_columns`, `join_paths`, resolved 필터를 정본으로 사용한다.
- `SELECT *`를 금지한다.
- 생성 실패 후 제한된 재시도를 수행한다.
- DB 실행 검증을 통과한 SQL만 `generated`로 확정한다.
- 월 팩트 0건이면 일 팩트로 한 번 재계획하는 복구 경로가 있다.

한계:

- 실행 성공은 업무 의미 정답을 보장하지 않는다.
- 검증 결과 0행을 일반 실패로 보지 않는다.
- 비어 있지 않은 결과도 잘못된 집계, 중복 JOIN, fan-out, 잘못된 GROUP BY를 포함할 수 있다.
- Q1에서 실제 1,744,952개 중간행 fan-out이 검증을 통과했다.
- Q2에서 평균의 가중치와 2020–2026 전기간 범위가 확정되지 않은 채 검증을 통과했다.
- `validate_max_rows=5`는 실행 가능성 확인에는 충분하지만 집계 정확성 확인에는 부족하다.
- 월→일 재계획은 특정 사례 전용 복구다. 일반화된 대체 계획 평가 정책은 아니다.
- SQL 재시도 시 첫 실패 원인이 계획 오류인지 생성 오류인지 구분이 약하다.

필요 검증:

- SQL AST가 계획 테이블·컬럼·JOIN·필터·집계와 일치하는지 검사
- JOIN cardinality와 집계 fan-out 위험 검사
- 필수 필터 누락 검사
- 질문의 aggregation과 SQL 함수 일치 검사
- `answer_axis`와 SELECT/GROUP BY 일치 검사
- 기간 필터 경계와 timezone 검사

### 2.5 API 계약: 보통

좋은 점:

- `/t2sql`은 SQL 확정, `/query_execute`는 결과 조회로 역할이 분리돼 있다.
- 요청 기본값과 런타임 설정 관계를 문서화했다.
- 성공·실패 코드가 구분돼 있다.
- 응답에 분석·계획·사용 메타데이터를 남긴다.

개선 필요:

- `column_top_m`은 요청 필드로 열려 있지만 Serving `/t2sql`에서 사용되지 않는다. 사용자에게 동작하는 옵션처럼 보이는 계약 결함이다.
- `auto_resolve_entities=false`여도 필터와 confirm은 유지된다. 이름만 보면 자동 값 해석 전체가 꺼질 것으로 오해할 수 있다.
- `include_matched_columns=false`는 내부 계산을 줄이지 않고 응답만 비운다. 동작은 문서화됐지만 필드 이름만으로는 알기 어렵다.
- 실패 응답의 `sql`은 실행 가능한 결과처럼 소비될 수 있다. `draft_sql`로 분리하거나 기본 미노출이 안전하다.
- `/t2sql` 검증과 `/query_execute` 실제 실행 사이에 데이터·스키마·Serving snapshot이 바뀔 수 있다.
- 실제 `/query_execute`의 한글 결과가 mojibake로 반환됐다. SQL 생성 성공과 별개로 최종 사용자 결과가 훼손된다.

권고:

- 미사용 `column_top_m` 제거 또는 실제 적용
- `auto_resolve_entities`를 `include_resolved_entities`와 같은 실제 의미로 개명
- 실패 초안은 별도 디버그 필드와 권한으로 분리
- 응답에 `metadata_snapshot_id`, `source_instance_id`, `validated_at` 포함
- `/query_execute`에서 `generation_id` 또는 SQL fingerprint 검증 지원
- connector→MindsDB→API 각 구간의 문자열 인코딩 계약을 UTF-8로 고정하고 한글 회귀 테스트 추가

### 2.6 관측성·운영성: 보통

강점:

- `generation_id`로 요청 단위 추적이 가능하다.
- 단계별 실패 사유 코드가 있다.
- probe 실행 내역과 사용 메타데이터를 응답한다.
- 전체 timeout과 단계별 timeout이 구분돼 있다.
- 외부 LLM, repository, MindsDB 실패를 분리할 기반이 있다.

부족한 정보:

- 단계별 소요 시간
- 의미 분석, 코드 매핑, 팩트 선정의 후보 수와 선택 점수
- 각 후보가 탈락한 이유
- LLM 모델·프롬프트 버전
- 메타데이터 snapshot ID
- 생성 시도별 DB 오류 유형
- 재시도 전후 SQL fingerprint
- timeout 발생 단계와 남은 budget
- SQL 생성·가드·validation 단계 로그
- JOIN 경로의 confidence와 complete 판정 근거
- `/query_execute` 결과 변환 전후 인코딩 정보

권고 이벤트:

- `analysis_completed`
- `mapping_candidates_selected`
- `fact_selection_completed`
- `plan_gate_rejected`
- `probe_completed`
- `confirm_completed`

각 이벤트에 `generation_id`, stage duration, snapshot ID, 후보 수, 결정 근거를 구조화해 기록한다. 실측에서는 로그가 confirm 생략 후 HTTP 200으로 끝나 생성·검증 과정을 추적할 수 없었다.

- 파일과 함수 위치를 제공한다.
- “하지 않는 것”과 “실제 동작”을 명확히 구분한다.
- 알려진 라벨 제거 문제도 숨기지 않는다.

개선점:

- 현재 동작, 설계 의도, 알려진 결함이 같은 수준으로 섞여 있다.
- 운영 보장 사항과 예시 기반 설명을 구분해야 한다.
- 단계별 입력·출력 계약과 불변조건이 없다.
- 설정값의 출처, 우선순위, 적용 지점을 한곳에서 보기 어렵다.
- 문서가 길어 변경 시 코드와 불일치할 위험이 크다.

## 3. 단계별 핵심 판정

### 요청·런타임

- 판정: 보통
- 이유: timeout과 기본값은 명확하다. 미사용 필드와 이름-동작 불일치가 있다.

### 의미 분해

- 판정: 보통
- 이유: 스토어 물리명 오염을 막는 설계는 좋다. LLM 실패 시 검색 품질 저하가 크고 설정 의존성이 복잡하다.

### 조회 문자열 생성

- 판정: 보통 이하
- 이유: 결정적이고 설명 가능하다. 표현 변형과 오탈자에 약하다.

### 값 코드 매핑

- 판정: 개선 필요
- 이유: fail-closed는 좋다. 단일 코드 확정과 짧은 라벨 삭제가 오답을 확정할 수 있다.

### 카탈로그·FK 확장

- 판정: 양호
- 이유: 승인 메타데이터와 FK로 후보 공간을 제한한다. 검색 recall 부족이 선행 병목이다.

### 팩트 선정

- 판정: 보통
- 이유: 입도와 subject area를 고려한다. 후보 경합을 해결할 근거 점수와 확인 경로가 부족하다.

### QueryPlan

- 판정: 개선 필요
- 이유: 구조화 자체는 좋다. Q1에서 필요 없는 별량·태그가 포함됐고, Q1·Q2 모두 0.28–0.35 신뢰도 JOIN을 가진 채 `complete`가 됐다.

### 생성 전 게이트

- 판정: 우수
- 이유: 메타데이터·범위·팩트·소스가 불완전하면 생성하지 않는다.

### Probe·Confirm

- 판정: 보통 이하
- 이유: 불필요한 probe 절감은 좋다. resolved 코드 존재만으로 confirm을 생략하면 앞 단계 오선정을 검증하지 못한다.

### SQL 생성·검증

- 판정: 보통
- 이유: 제한 생성, allowlist, 실행 검증은 동작했다. Q1 fan-out과 Q2 집계 의미·기간 불확정도 모두 `generated`를 통과했다.

### 응답

- 판정: 개선 필요
- 이유: 추적 정보는 풍부하다. `/query_execute` 한글 결과 깨짐, 실패 SQL 초안 노출, snapshot 식별 부족이 있다.

## 4. 우선순위 개선안

### P0 — 정확성·안전성

#### P0-1. 계획 정합성 검증기 추가

SQL 생성 전에 다음 불변조건을 코드로 검사한다.

- 모든 resolved 필터가 질문의 범위 또는 측정 언급과 연결됨
- 팩트가 metric과 승인 컬럼으로 연결됨
- 모든 required table이 승인 FK 경로로 연결됨
- 모든 required table이 질문 역할 또는 답 산출에 실제 필요함
- answer axis가 SELECT/GROUP BY 후보 컬럼으로 존재
- aggregate 질문에 집계 대상과 집계 함수가 존재
- `complete` 판정에 최소 JOIN confidence 기준 적용

완료 기준:

- 잘못된 코드, 단절된 팩트, 불완전 JOIN 계획이 생성 단계 전에 `PLAN_INCOMPLETE`로 종료됨
- Q1 계획에서 `rdibyun_tb`, `rditag_tb`가 제거되고 1,744,952행 fan-out이 사라짐

#### P0-2. 집계·기간 의미 계약 추가

QueryPlan에 다음을 명시한다.

- aggregation function
- base value column
- weighted 여부와 weight column
- null·이상치 처리
- time scope
- 데이터 최신일
- 다중 태그 결합 방식

기간 없는 집계 질문은 업무 정책에 따라 다음 중 하나로 처리한다.

- 명시된 기본 기간 적용 후 응답에 고지
- 전체 기간 적용 후 최소·최대 일자 고지
- `unresolved_requirements`로 사용자 확인 요구

완료 기준:

- Q2의 `AVG(VAL)` 선택 근거와 2020-01-01~2026-12-31 범위가 계획·응답에 명시됨
- `CNT` 가중 여부가 LLM 추론이 아닌 메타데이터 계약으로 결정됨

#### P0-3. SQL AST 기반 가드 적용

문자열 포함 여부가 아닌 파싱된 SQL 구조로 검사한다.

- 단일 statement와 SELECT 계열 확인
- 실제 object reference 확인
- ON 절의 테이블 쌍·컬럼 쌍·연산자 확인
- WHERE 필수 코드 필터 확인
- SELECT와 GROUP BY 정합성 확인
- 계획 밖 서브쿼리 객체 차단
- 불필요한 JOIN과 예상 cardinality 급증 차단

완료 기준:

- 승인 컬럼명만 임의로 넣어 가드를 우회하는 SQL이 모두 거부됨
- 목록 질의의 JOIN 예상행이 기준 엔티티 수보다 비정상적으로 커지면 거부 또는 경고

#### P0-4. 코드 매핑 확정 정책 수정

- distinct 코드 1개만으로 자동 확정하지 않음
- exact mention, 엔티티 유형, 표·컬럼 역할, 질문 문맥을 함께 평가
- 괄호 라벨은 삭제 대신 동률 후보로 유지
- 후보 충돌 시 자동 확정 금지

완료 기준:

- 같은 머리 라벨에 다른 코드가 있는 테스트에서 임의 행 삭제가 발생하지 않음
- 낮은 신뢰도 단일 후보가 `resolved`로 확정되지 않음

#### P0-5. 실패 SQL 초안 실행 방지

- 실패 응답의 `sql`을 기본 `null`로 처리
- 필요 시 관리자 디버그 응답의 `draft_sql`로 분리
- `/query_execute`는 generated 상태 또는 서명된 fingerprint만 허용하는 방안 검토

완료 기준:

- `validation_failed` 또는 `failed` 응답에서 일반 클라이언트가 초안을 실행할 수 없음

#### P0-6. `/query_execute` 한글 인코딩 수정

- 원천 connector 반환 인코딩 확인
- MindsDB 결과 문자열 decode 지점 확인
- Latin-1 성격의 byte-to-character 변환 제거
- JSON 응답을 UTF-8 Unicode 문자열로 직렬화

완료 기준:

- `SUJ_NAME`, `BNB_NAME`이 원문 한글로 반환됨
- ASCII, 한글, 괄호, 공백이 섞인 명칭 round-trip 테스트 통과
- `/t2sql` 메타데이터 값과 `/query_execute` 결과값의 문자열 인코딩 일치

### P1 — 성공률·운영성

#### P1-1. 후보 점수와 근거 도입

각 값·표·팩트 후보에 다음을 기록한다.

- match type
- normalized mention
- matched metadata field
- confidence score
- 선택·탈락 사유

#### P1-2. confirm 역할 강화

confirm은 resolved 값 존재 여부가 아니라 다음을 검증한다.

- 질문 언급과 natural value의 의미 일치
- 코드 엔티티 유형 일치
- 범위 코드와 선택 표의 적용 가능성
- metric과 fact 컬럼 일치

#### P1-3. 의미 검색을 후보 생성에 제한 도입

- exact·approved alias 우선
- 의미 검색은 recall 보강
- 최종 확정은 승인 메타데이터 관계와 임계값 사용

#### P1-4. 단계별 telemetry 추가

- stage duration
- 후보 수
- 선택 근거
- 모델·프롬프트 버전
- snapshot ID
- validation 오류 유형

#### P1-5. API 필드 정리

- `column_top_m` 제거 또는 적용
- `auto_resolve_entities` 개명
- 실패 초안 필드 분리
- snapshot과 validation fingerprint 추가

### P2 — 확장성·문서 유지관리

- 규칙형 접미 사전을 메타데이터 관리 대상으로 전환
- 다중 범위, 제외 조건, OR 조건 지원
- 사용자 확인이 필요한 ambiguity 응답 계약 추가
- 문서와 코드 계약을 자동 생성 또는 테스트로 연결
- 월→일 이외의 일반 fallback 정책 설계

## 5. 필수 테스트 권고

### 값매핑

- 같은 머리 라벨, 다른 괄호 설명, 다른 코드
- 같은 natural value가 다른 엔티티 유형에 존재
- exact 후보 1개지만 질문 문맥과 유형 불일치
- 범위 접미만 존재하고 사례 없음
- 범위 코드 0개, 1개, 2개 이상
- 오탈자·띄어쓰기·약칭·동의어

### 팩트 선정

- 동일 metric의 일·월·시간 팩트 동시 존재
- 후보 2개가 모두 JOIN 가능
- Raw와 Fact가 동시 적중
- 기간 없음, 월별, 주간, 연 구간
- metric은 같지만 단위가 다른 팩트

### JOIN·집계

- 승인 컬럼명은 있으나 잘못된 테이블 쌍으로 JOIN
- 올바른 JOIN이지만 1:N fan-out으로 평균 왜곡
- Q1에서 태그·별량 없이 79개를 반환하고 중간행 급증이 없는지
- Q2에서 `AVG(VAL)`과 `CNT` 가중 평균 정책이 명시되는지
- 기간 없는 평균의 실제 최소·최대 일자를 응답하는지
- 현재일 이후 데이터 포함 정책이 적용되는지
- answer axis 누락
- GROUP BY 누락 또는 과다
- 필수 코드 필터 누락
- 잘못된 aggregation 함수

### 가드

- 다중 statement
- 주석 뒤 비조회 statement
- CTE 내부 비승인 테이블
- 계획 밖 서브쿼리
- alias로 숨긴 비승인 객체
- 실패 SQL 초안의 `/query_execute` 호출
- 질문과 무관한 required table 추가
- 낮은 confidence JOIN만으로 `complete` 판정

### 응답 인코딩

## 6. 권장 품질 지표

- 계획 정확도: 정답 테이블·코드·팩트·JOIN을 모두 선택한 비율
- SQL 의미 정확도: 결과가 기준 SQL과 의미상 일치한 비율
- unsafe SQL 차단율
- 정상 SQL 오차단율
- ambiguity 검출 재현율
- 의미 분석 degraded 비율
- 단계별 timeout 비율
- 0행 validation 비율
- 재시도 성공률
- 질문 유형별 성공률
- p50/p95 전체 지연시간

운영 승인 기준은 단순 SQL 생성률이 아니라 **의미 정확도와 위험 SQL 차단율**을 중심으로 정해야 한다.

## 7. 최종 평가

현재 설계의 핵심 방향은 타당하다.

> 자연어 → 의미 슬롯 → 승인 메타데이터 검색 → 코드·팩트·JOIN 계획 → 제한된 SQL 생성 → DB 검증

이 구조는 LLM 단독 Text-to-SQL보다 통제 가능하고 감사 가능하다. 생성 전 게이트와 실행 검증도 실운영에 적합한 기반이다.

다만 정확성 병목은 LLM SQL 생성보다 앞단에 있다.

1. 문자열 중심 후보 검색
2. 단일 코드 자동 확정
3. 짧은 라벨 소거
4. 팩트 휴리스틱
5. resolved 값 존재 시 confirm 생략
6. 실행 성공 중심 검증
7. JOIN 필요성·cardinality 미검증
8. 집계 가중치·기간 계약 부재

실API 검증으로 다음 문제가 확인됐다.

- Q1: 79개 목록 전에 1,744,952개 중간행 생성
- Q2: 2020–2026 전기간 17개 태그를 설명 없이 평균
- Q2: `AVG(VAL)`과 `CNT` 가중 평균의 업무 의미 미확정
- Q1·Q2: 최저 0.28 JOIN confidence인데 `complete`
- Q1·Q2: resolved 코드 존재로 confirm 생략
- `/query_execute`: 한글 명칭 깨짐

따라서 다음 개발 순서는 **프롬프트 개선보다 JOIN 필요성·cardinality 검증, 집계·기간 계약, 한글 인코딩 수정, 계획 검증기, AST 가드 강화가 우선**이다.

P0 항목 적용 후에는 안전성과 추적성뿐 아니라 의미 정확성까지 보장하는 메타데이터 기반 T2SQL 엔진으로 발전할 수 있다.
